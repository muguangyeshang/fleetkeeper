# fleetkeeper 使用说明书

这份说明给第一次拿到这个工具、电脑上跑着几个本地服务的人看。按第一条路走，全程不用装 Python，不用开终端，不用记命令，不用联网。

## 一 它管什么事

电脑上常驻着好几个本地服务，网关、模型服务、任务脚本、抓取程序。它们出问题的时候，进程往往还在。端口还开着，请求全卡住，或者主循环卡死，活儿早停了。人往往到第二天才发现。

这个工具每分钟看一遍这些服务，按证据判断它们到底算不算活着，挂了就按你写的命令拉起来，同时把事情记下来、通知出去。它额外做了几件别的看门狗不太做的事，断网的时候不动手，避免把一次断网放大成一堆僵尸进程；自己改配置的时候会先抢锁，避免几个程序互相覆盖；日志和通知发出去之前会把密钥抹掉。

它不会偷偷装服务、写注册表、开机自启、连外部服务器。关掉窗口就停。

### 谁该装，谁别装

该装的情况。同一台电脑上常驻两三个以上本地服务，比如 AI 网关、模型服务、队列脚本、抓取程序。半夜有东西停了，第二天才有人发现。你就是那个要把它拉起来的人。

不用装的情况。只跑一个进程而且系统已经会自动重启，需要监控很多台机器、要公开状态页、要几十种通知渠道，或者电脑上根本没有常驻服务。前两种去找 Gatus 或 Uptime Kuma，最后一种打开之后没东西可看。

这个工具做不了集群，不做图表，不做云端同步。它只管一台机器上的一次安全重启。

## 二 三种打开方式

| 方式 | 需要什么 | 怎么开始 | 适合谁 |
| --- | --- | --- | --- |
| `fleetkeeper.exe` 双击 | 只有这一个文件，8 MB 左右 | 随便放进一个空文件夹，双击 | 自己电脑上跑着几个本地服务的人 |
| `start.bat` 双击 | 本机装了 Python | 在项目目录里双击 `start.bat` | 已经从源码装过的人 |
| 命令行 `fleetkeeper` | 装了 Python 并 `pip install -e .` | 敲 `fleetkeeper`，不带任何参数，同样会开网页 | 要写脚本、接定时任务的人 |

exe 用 `scripts\build_exe.bat` 生成，生成物在 `dist\fleetkeeper.exe`。exe 不进仓库，将来会挂在 GitHub Release 附件上。构建那台机器需要 Python 和 `pyinstaller`，用 exe 的机器什么都不需要。

## 三 第一次打开会发生什么

按顺序，这些是真跑过的行为。

1. 弹出一个黑色命令行窗口。这个窗口就是程序本体，别关，关了服务就停。窗口里会打印两行提示。
2. 程序在 exe 同目录生成 `fleet.json`。里面预先放了一个占位服务 `Example Service`，端口是 8080。
3. 网页服务只绑在 `127.0.0.1` 的一个随机空闲端口上，外部机器连不上。
4. 默认浏览器自动打开中文页面「服务守护面板」。没自动打开的话，手动复制黑窗口里那行网址。
5. 页面第一次加载会列出占位服务，卡片通常是红的。这是正常的，占位端口上没有你的服务，程序本身没坏。想省事就在页面顶部选一个场景点「套用场景」，或者填一个服务名和端口点保存，占位服务自动被替换掉。

内置三个场景。本地 AI 三件套写入 Ollama、AI 网关、队列三个服务，端口分别是 11434、8080、8081。Ollama 那条还带一个真实的业务探针，会去请求 `/api/tags` 并检查返回的模型列表。存活检查走根路径，业务探针走另一个地址，这样才算真的验证了业务。两个地址写成一样的话，程序只会给 L3，不会算业务通过。单个 HTTP 服务只有一个端口可以改。空白起步就是原来那个占位。套用之后按自己电脑上的真实端口改。已经保存过自己的服务时，套用会先弹一次确认。命令行写法是 `fleetkeeper init --preset local-ai`，`fleetkeeper init --list-presets` 可以列出全部场景。

黑窗口里那一轮实测输出长这样，路径和端口每次不同。

```
第一次使用，已自动生成配置文件：...\fleet.json
服务守护面板：http://127.0.0.1:51472/
页面已在浏览器中打开。按 Ctrl+C 或关掉本窗口即可停止。
```

页面上没有 CDN、没有外链字体、没有外部脚本。断网也能开。

## 四 页面上的按钮各干什么

| 按钮 | 背后的接口 | 实际发生的事 |
| --- | --- | --- |
| 立即体检 | `GET /api/state` | 重新读配置，对每个服务跑一遍证据判定，刷新卡片 |
| 跑一次守护 | `POST /api/sweep` | 执行一次完整检查，含闸门判断、拉起、告警、记事件 |
| 打开完整报告 | `GET /report` | 另开一个自包含 HTML 页，可另存到本地 |
| 最近发生了什么 | `GET /api/history` | 从 sqlite 读最近的巡检和告警事件 |
| 保存（服务名加端口） | `POST /api/service` | 写回 `fleet.json`，第一次保存会移除占位服务 |
| 套用场景 | `POST /api/preset` | 用内置场景替换服务列表，已有自己的服务时要先确认 |
| 停止程序 | `POST /api/stop` | 关闭本地网页服务，黑窗口退出 |

页面每 5 秒自己刷新一次状态。所有写操作都落在 exe 同目录的 `fleet.json`。

## 五 配置文件里每一项

`fleet.json` 是普通 JSON，可以直接用记事本改。下面这些是 `init` 实际生成的字段，路径全部相对配置文件所在目录。

| 字段 | 生成时的值 | 改它会怎样 |
| --- | --- | --- |
| `registry.defaults.heartbeat_period` | 60 | 所有服务共用的心跳周期，单位秒。服务自己写了同名值就用自己的 |
| `registry.services.<key>.name` | `Example Service` | 页面上显示的名字 |
| `registry.services.<key>.port` | 8080 | 要盯的端口。改端口是最常见的一步 |
| `registry.services.<key>.health.path` | `/` | 协议探测用的 HTTP 路径 |
| `registry.services.<key>.health.method` | `GET` | 探测方法 |
| `registry.services.<key>.health.timeout` | 3 | 单次探测超时，秒 |
| `registry.services.<key>.canary` | 空 | 业务探针，填了才有机会升到 L4 |
| `registry.services.<key>.recovery` | 空 | 服务挂了要执行的启动脚本。留空就只报告、不拉起 |
| `registry.services.<key>.logs.stderr` 或 `logs.stdout` | 无此字段 | 写了之后 `logs 服务名` 能读日志，默认会脱敏 |
| `watchdog.state_file` | `runtime/watchdog-state.json` | 冷却、阈值、告警状态存在这里 |
| `watchdog.threshold` | 2 | 连续异常几轮才发第一次告警 |
| `watchdog.re_alert_interval` | 15 | 持续异常时每隔几轮重发一次 |
| `watchdog.heal_cooldown_seconds` | 180 | 每个端口单独的拉起冷却，秒 |
| `watchdog.net_probe_targets` | 空列表 | 断网闸门的目标。空列表表示闸门关闭。填上 `["1.1.1.1", 443]` 这类目标才会启用 |
| `watchdog.net_probe_timeout` | 3.0 | 断网探测超时，秒 |
| `watchdog.pause_gates` | 空对象 | 暂停标记，写法见第七节 |
| `watchdog.alert_log` | `runtime/alerts.log` | 告警文本日志，一直开着 |
| `watchdog.history_file` | `runtime/history.sqlite3` | 事件时间线 |
| `watchdog.history_retention_days` | 30 | 事件保留天数，写 0 表示永久保留 |
| `watchdog.notify.channels` | `["webhook", "command"]` | 要启用的通道，少写就少发 |
| `watchdog.notify.webhook_url` | 空 | 填上 URL 才会 POST，留空就没有这个通道 |
| `watchdog.notify.webhook_timeout` | 3.0 | POST 超时，秒 |
| `watchdog.notify.command` | 空 | 外部命令，收到同一份 JSON，从标准输入读 |
| `watchdog.notify.command_timeout` | 10.0 | 外部命令超时，秒 |

顶层还可以写 `heartbeat_dir`，默认 `runtime/heartbeat`，心跳文件放这里。

`registry.defaults` 里的字段会合并进每个服务，服务自己写的优先。完整的字段取值和 canary 写法在 `USER_GUIDE.md`。

## 六 看懂卡片上的标记

| 标记 | 含义 |
| --- | --- |
| `L0_CONFIG` | 只在配置里声明了，没找到监听进程 |
| `L1_PROCESS` | 找到监听进程，端口还没验通 |
| `L2_PORT` | 恰好一个进程在监听，TCP 能连上 |
| `L3_PROTOCOL` | HTTP 状态行回来了。5xx 算活着但生病 |
| `L4_BUSINESS` | 业务探针通过，这是程序能自己拿到的最高证据 |
| `P0` | 真的坏了，医生报告里会列进失败清单 |
| `??` | 证据不够，程序拒绝说它健康，也拒绝说它坏了 |
| `NO_HEARTBEAT` | 服务没接心跳，端口通也证明不了它在干活 |
| `ALIVE_ONLY` / `PROTOCOL_ONLY` | 弱证据，不会被当成正常 |
| `FAILING` / `STALE` | 最近一次业务尝试失败，或者成功记录太旧 |

`L4` 加 `??` 同时出现是正常的。业务探针过了，但服务没有心跳，程序不会替它宣布一切正常。`L5` 表示人真的拿到了想要的结果，程序永远不自动认领这一级。

## 七 为什么挂了却没自动拉起来

五种情况会挡住拉起动作，每一种都能在配置里找到对应项。

| 闸门 | 判断依据 | 相关字段 |
| --- | --- | --- |
| 断网闸门 | 所有探测目标都连不上，这一轮只记录不拉起 | `net_probe_targets` |
| 连续阈值 | 没到 `threshold` 轮，先观察 | `threshold` |
| 端口冷却 | 这个端口刚拉过，还没过冷却期，别的端口不受影响 | `heal_cooldown_seconds` |
| 暂停标记 | 标记文件存在，认为有人故意停了这个服务 | `pause_gates` |
| 没写启动命令 | `recovery` 为空，本来就没有东西可执行 | `registry.services.<key>.recovery` |

暂停标记写法示例，把 `PAUSE_LLM` 这个文件放到配置同目录，端口 1234 就进入暂停。

```json
"pause_gates": {
  "local-llm": { "ports": [1234], "marker_file": "PAUSE_LLM" }
}
```

还有一层保护在代码里，进程操作只按 PID 做，动作之前会核对命令行，没有按进程名批量杀的入口。

## 八 命令行四步

装过 Python 包的人可以按这个顺序走。`--config` 放在子命令前后都一样。

```bash
fleetkeeper init --config fleet.json --port 8080
fleetkeeper --config fleet.json doctor
fleetkeeper --config fleet.json sweep
fleetkeeper --config fleet.json history --last 24h
```

一次真实运行里，一个本地 HTTP 服务活着并配了业务探针，另一个端口没人监听，输出如下。

```
$ fleetkeeper --config fleet.json doctor
fleetkeeper doctor  2026-11-06T18:13:31+0800
====================================================================
[??] LLM Gateway            :59201  L4_BUSINESS
      heartbeat: NO_HEARTBEAT  service has no heartbeat; it cannot prove it is working
[P0] Dead Worker            :59202  L0_CONFIG
      heartbeat: NO_HEARTBEAT  service has no heartbeat; it cannot prove it is working
====================================================================
P0 failures (broken for real):
  - Dead Worker :59202
      no process listening

Insufficiently covered (not failures, but work is unproven):
  - LLM Gateway : heartbeat=NO_HEARTBEAT
  a live port proves the process is not dead; it does not prove work.

$ fleetkeeper --config fleet.json sweep
issue: Dead Worker(:59202) no process listening

$ fleetkeeper --config fleet.json history --last all
TIME                    KIND    LEVEL     SERVICE                  ISSUES MESSAGE
2026-11-06 18:13:32.784 sweep   warning   Dead Worker              1      1 issue(s), 0 healed, 0 alert(s)

1 event(s) shown; total in db: 1. '--last all' shows everything.
```

第一轮 `sweep` 只打印 issue，不发告警，因为默认 `threshold` 是 2。连续第二轮异常才会触发告警和通知。时间线里的时间戳带毫秒，同一秒跑几次也分得出先后。

想看画面就加 `--html`。

```bash
fleetkeeper --config fleet.json doctor --html status.html
```

生成的是一个文件，双击就能打开，没有 CDN、没有脚本、没有外链。仓库里 `docs/assets/status-page.html` 是一份真实生成的样例，可以先点开看。

## 九 出问题怎么查

| 现象 | 原因 | 怎么处理 |
| --- | --- | --- |
| 双击 exe 没反应 | 窗口一闪而过，可能端口被占或配置损坏 | 在文件夹地址栏敲 `cmd`，再敲 `fleetkeeper.exe` 看报错 |
| 浏览器没打开 | 系统没设默认浏览器 | 复制黑窗口里那行 `http://127.0.0.1:.../` 手动粘 |
| 所有服务都是 L0 | 本机没有 `netstat`，也拿不到监听表 | 装可选依赖 `psutil`，或者改用有 `netstat` 的系统 |
| 端口明明通，却显示 `??` | 服务没接心跳，或者没有业务探针 | 按 `USER_GUIDE.md` 接一行心跳，或者填 `canary` |
| 配了 canary 还停在 L3 | 探针路径和健康检查是同一个地址，被判定为只证明协议 | 把 canary 换到真实业务路径 |
| `sweep` 什么都没发 | 还没到 `threshold`，或者 `notify` 两个通道都留空 | 多跑一轮，或者填 `webhook_url` / `command` |
| 一直显示断网、不自愈 | `net_probe_targets` 里的目标全连不上 | 换成自己网络能通的探测目标，或者清空列表关掉闸门 |
| 配置改了没生效 | 改的不是程序实际读的那份 `fleet.json` | 看黑窗口打印的路径，路径都相对配置文件所在目录 |
| 时间线查不到东西 | 还没跑过 `sweep`，或者 `--last` 窗口太短 | 先跑一次 `sweep`，再用 `--last all` 看全部 |

`notify` 里某个通道挂了不会拖垮整轮巡检，输出会写 `error ...`，该拉起的服务照样拉起。

## 十 文件都写在哪

所有运行时文件都在配置文件同目录的 `runtime/` 下。

```
runtime/
  watchdog-state.json     冷却、连续异常计数、告警状态、断网起始时间
  alerts.log              告警文本，一行一条
  history.sqlite3         巡检与告警事件，追加写入
  heartbeat/              每个服务一个心跳 JSON
```

`state.json` 是快照，时间线是追加流，后者不会被覆盖。想从零开始，停掉程序删掉 `runtime/` 即可。

## 十一 怎么停、怎么卸

点页面右上「停止程序」，或者在黑窗口按 `Ctrl+C`，或者直接关窗口。三种都行。

这个程序不注册服务、不写计划任务、不改注册表、不开机自启。要卸掉就删掉那个文件夹。定时任务是你自己加的，删任务的时候记得一起删，Windows 在「任务计划程序」里，Linux 在 `crontab -e` 里。
